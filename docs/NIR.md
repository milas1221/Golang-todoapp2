ТЕРМИНЫ И ОПРЕДЕЛЕНИЯ

В настоящем отчёте применяются следующие термины с соответствующими определениями.

REST (Representational State Transfer) — архитектурный стиль взаимодействия компонентов распределённого приложения в сети, основанный на принципах использования стандартных HTTP-методов для выполнения операций над ресурсами.

API (Application Programming Interface) — программный интерфейс приложения, представляющий собой набор определённых правил и спецификаций, посредством которых одна программа может взаимодействовать с другой.

CRUD (Create, Read, Update, Delete) — четыре базовые операции, используемые при работе с хранилищами данных: создание, чтение, обновление и удаление записей.

Middleware — промежуточное программное обеспечение, представляющее собой обработчик, включённый в цепочку обработки HTTP-запросов, выполняющий вспомогательные функции до или после основного обработчика.

Docker — платформа для разработки, доставки и запуска приложений в изолированных контейнерах, обеспечивающая воспроизводимость среды выполнения.

Graceful Shutdown — механизм корректного завершения работы серверного приложения, при котором прекращается приём новых запросов, но завершаются все текущие обработчики.

Optimistic Locking (оптимистичная блокировка) — стратегия управления конкурентным доступом к данным, при которой при обновлении записи проверяется, что её версия не изменилась с момента чтения.

UUID (Universally Unique Identifier) — универсальный уникальный идентификатор, представляющий собой 128-битное число, используемое для идентификации объектов в распределённых системах.

JSON (JavaScript Object Notation) — текстовый формат обмена данными, основанный на подмножестве языка JavaScript, широко используемый в REST API для передачи структурированных данных.

Swagger/OpenAPI — спецификация для описания, создания, использования и визуализации RESTful веб-сервисов, позволяющая автоматически генерировать интерактивную документацию.

PostgreSQL — свободная объектно-реляционная система управления базами данных с открытым исходным кодом, обеспечивающая надёжность, целостность данных и поддержку расширенных SQL-запросов.

Go (Golang) — компилируемый многопоточный язык программирования, разработанный компанией Google, ориентированный на создание высокопроизводительных сетевых сервисов и серверных приложений.

Clean Architecture (чистая архитектура) — архитектурный подход, предложенный Робертом Мартином, основанный на разделении системы на слои с направлением зависимостей от внешних слоёв к внутренним, обеспечивающий независимость бизнес-логики от деталей реализации.

1 Анализ предметной области

1.1 Системы управления задачами: назначение и классификация

Системы управления задачами (Task Management Systems) представляют собой класс программного обеспечения, предназначенного для планирования, отслеживания и контроля выполнения задач. Такие системы позволяют пользователям создавать задачи, назначать им приоритеты, устанавливать сроки выполнения, отмечать степень завершённости и получать статистику по продуктивности.

По масштабу применения системы управления задачами можно классифицировать следующим образом:
— персональные Todo-приложения, ориентированные на индивидуальное использование для ведения списка дел;
— командные системы управления проектами, предоставляющие возможности совместной работы, распределения задач между участниками и контроля прогресса;
— корпоративные системы управления задачами, интегрированные с бизнес-процессами организации и включающие расширенные средства аналитики и отчётности.

По архитектуре реализации выделяют:
— настольные приложения, устанавливаемые локально на рабочую станцию пользователя;
— веб-приложения, доступные через браузер и не требующие установки;
— мобильные приложения для платформ iOS и Android;
— кроссплатформенные решения, объединяющие веб- и мобильные интерфейсы с синхронизацией данных через облачное хранилище.

В контексте настоящего исследования рассматриваются многопользовательские веб-приложения для управления задачами с REST API интерфейсом, что обеспечивает возможность интеграции с различными клиентскими приложениями.

Приложение предоставляет REST API для интеграции со сторонними сервисами, поддерживает совместную работу, приоритеты задач и визуализацию продуктивности. 2 Исследование методов и технологий разработки

2.1 Архитектурные подходы к проектированию веб-приложений

При проектировании серверных веб-приложений ключевым решением является выбор архитектурного подхода, определяющего структуру кода, направление зависимостей и способы взаимодействия компонентов системы.

2.1.1 Монолитная архитектура

Монолитная архитектура представляет собой традиционный подход, при котором все компоненты приложения размещаются в единой кодовой базе и развёртываются как одно целое. Основным преимуществом является простота разработки и развёртывания на начальных этапах. Однако по мере роста системы монолитная архитектура приводит к высокой связанности компонентов, затрудняет тестирование и масштабирование.

2.1.2 Многослойная (layered) архитектура

Многослойная архитектура предполагает разделение приложения на логические слои, каждый из которых отвечает за определённый аспект функциональности. Классическая трёхслойная архитектура включает:
— слой представления (Presentation Layer), отвечающий за обработку HTTP-запросов и формирование ответов;
— слой бизнес-логики (Business Logic Layer), содержащий правила предметной области;
— слой доступа к данным (Data Access Layer), инкапсулирующий взаимодействие с базой данных.

Данный подход обеспечивает разделение ответственности (Separation of Concerns) и позволяет модифицировать один слой без влияния на остальные.

2.1.3 Чистая архитектура (Clean Architecture)

Чистая архитектура, предложенная Робертом Мартином [2], развивает идеи многослойной архитектуры, вводя строгое правило направления зависимостей: зависимости всегда направлены от внешних слоёв к внутренним. Внутренние слои (доменная модель, бизнес-логика) не зависят от внешних (фреймворки, базы данных, HTTP).

В контексте разрабатываемого приложения применяется адаптированный вариант многослойной архитектуры с элементами чистой архитектуры, включающий четыре слоя:

Рисунок 1 — Схема многослойной архитектуры приложения

[Transport (HTTP)] → [Service (бизнес-логика)] → [Repository (доступ к данным)] → [Database (PostgreSQL)]

— Transport — обработка HTTP-запросов, валидация входных данных, формирование ответов;
— Service — реализация бизнес-логики, оркестрация операций;
— Repository — абстракция доступа к данным, SQL-запросы;
— Domain — доменные сущности и бизнес-правила.

Интерфейсы репозиториев определяются в пакете сервиса (а не репозитория), что соответствует принципу инверсии зависимостей (Dependency Inversion Principle). Сервис владеет контрактом, а репозиторий его реализует.

| Простота развёртывания    | Один бинарный файл | Требует JVM | Требует интерпретатор | Требует runtime |

Язык Go выбран по следующим основаниям:
— встроенная поддержка конкурентности через горутины и каналы, что обеспечивает эффективную обработку множества одновременных HTTP-запросов;
— компиляция в один статический бинарный файл, упрощающая развёртывание и контейнеризацию;
— полноценный HTTP-сервер в стандартной библиотеке (пакет net/http), не требующий сторонних фреймворков;
— строгая статическая типизация, выявляющая ошибки на этапе компиляции;
— низкое потребление памяти, что критично для контейнерных сред;
— быстрое время компиляции, ускоряющее цикл разработки [1, 5].

2.3 Обоснование выбора СУБД PostgreSQL

В качестве системы управления базами данных выбрана PostgreSQL версии 18 [4]. Обоснование выбора:
— открытый исходный код и свободная лицензия, не ограничивающая коммерческое использование;
— поддержка UUID в качестве типа данных, что позволяет эффективно хранить идентификаторы сущностей;
— поддержка CHECK-ограничений для обеспечения целостности данных на уровне СУБД;
— поддержка транзакций с уровнями изоляции, необходимых для реализации оптимистичной блокировки;
— высокая надёжность и производительность, подтверждённые многолетней эксплуатацией в промышленных системах;
— наличие высококачественного драйвера pgx для языка Go с поддержкой пула соединений [13].

2.4 Технологии контейнеризации: Docker и Docker Compose

Для обеспечения воспроизводимости среды разработки и развёртывания применяются технологии контейнеризации Docker и Docker Compose [6].

Docker позволяет упаковать приложение вместе со всеми зависимостями в изолированный контейнер, который может быть запущен на любой платформе с установленным Docker Engine. Это устраняет проблему различий между средами разработки, тестирования и эксплуатации.

Docker Compose предоставляет декларативный способ описания многоконтейнерных приложений. В контексте разрабатываемой системы Docker Compose используется для оркестрации следующих сервисов:
— PostgreSQL — сервер базы данных;
— migrate — утилита для управления миграциями базы данных;
— port-forwarder — утилита для проброса портов базы данных на хост-систему;
— swagger — генератор Swagger-документации.

2.5 Протокол REST и спецификация OpenAPI/Swagger

REST (Representational State Transfer) — архитектурный стиль, предложенный Роем Филдингом в 2000 году [3], определяющий набор ограничений для проектирования распределённых систем. Ключевые принципы REST:
— использование HTTP-методов (GET, POST, PATCH, DELETE) для выполнения операций;
— адресация ресурсов через URI (Uniform Resource Identifier);
— отсутствие состояния (stateless): каждый запрос содержит всю необходимую информацию;
— единообразный интерфейс, упрощающий архитектуру.

Спецификация OpenAPI (ранее Swagger) [7] позволяет описать REST API в машиночитаемом формате и автоматически генерировать интерактивную документацию. В проекте используется библиотека swaggo/swag, которая генерирует OpenAPI-спецификацию на основе аннотаций в Go-коде, и библиотека swaggo/http-swagger для отображения Swagger UI.

2.6 Паттерны проектирования

2.6.1 Dependency Injection (внедрение зависимостей)

Внедрение зависимостей — паттерн проектирования, при котором зависимости объекта передаются ему извне, а не создаются внутри. В разрабатываемом приложении используется ручное внедрение зависимостей (без DI-контейнера): цепочка Repository — Service — HTTP Handler собирается в функции main.

Данный подход обеспечивает:
— слабую связанность компонентов (loose coupling);
— возможность замены реализации (например, PostgreSQL-репозитория на in-memory для тестирования);
— явное отображение графа зависимостей в точке сборки приложения.

2.6.2 Repository Pattern

Паттерн «Репозиторий» [11] инкапсулирует логику доступа к данным, предоставляя сервисному слою абстрактный интерфейс для работы с сущностями. Сервис оперирует доменными объектами и не знает о деталях SQL-запросов или структуры таблиц.

В проекте интерфейс репозитория определяется в пакете сервиса (согласно принципу Interface Segregation из SOLID [10]), а реализация — в отдельном пакете postgres. Это позволяет сервисному слою зависеть только от абстракции, а не от конкретной СУБД.

2.6.3 Optimistic Locking (оптимистичная блокировка)

Оптимистичная блокировка — стратегия управления конкурентным доступом, при которой при обновлении записи в условие WHERE включается текущая версия записи. Если версия изменилась (другой запрос успел обновить запись), операция UPDATE не затронет ни одной строки, и приложение вернёт ошибку конфликта (HTTP 409 Conflict).

В доменных сущностях Task и User присутствует поле Version, которое инкрементируется при каждом успешном обновлении. Данный подход не блокирует строки при чтении, что обеспечивает высокую пропускную способность.

2.6.4 Nullable-тип для PATCH-запросов

При обработке PATCH-запросов необходимо различать три состояния поля:
— поле не передано в запросе (не требует изменения);
— поле передано со значением null (необходимо установить NULL в БД);
— поле передано со значением (необходимо обновить).

Для решения этой задачи используется обобщённый тип Nullable[T] с двумя полями: Set (признак наличия поля в запросе) и Value (указатель на значение). Данный подход позволяет корректно обрабатывать частичные обновления с возможностью обнуления необязательных полей.
